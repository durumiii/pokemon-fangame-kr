# 절23 꼬리 개행 22행 조사

**대상**: `translate/ko/23-script-texts.jsonl`에서 `v`가 `\n`/`\r\n`으로 끝나는데
`k`는 그렇지 않은 행.

**재현 명령**:
```python
import json
path = "translate/ko/23-script-texts.jsonl"
out = []
with open(path, encoding='utf-8') as f:
    for i, line in enumerate(f, 1):
        obj = json.loads(line)
        if 'v' not in obj or 'k' not in obj:
            continue
        k, v = obj['k'], obj['v']
        v_nl = v.endswith('\r\n') or v.endswith('\n')
        k_nl = k.endswith('\r\n') or k.endswith('\n')
        if v_nl and not k_nl:
            out.append((i, k, v))
```
결과: **22행**(실측, 위 스크립트 실행 출력).

## 결론 먼저

22행 중 **9행은 두어야 하고(게임이 실제로 그 개행을 요구하는 자리), 13행은 아무 쪽으로
해도 무방하다(죽은 키라 게임이 조회조차 안 한다)**. 어느 행도 「떼야 한다」로 판정되지
않았다 — 뗀다고 눈에 보이는 문제가 생기진 않지만(죽은 13행), 둔다고 문제가 생기는
행도 하나도 없었다(실측: 살아 있는 9행 전부 개행이 있어야 정상).

## 조사 1 — 원문(k) 쪽 대칭성 (실측)

`translate/ko/23-script-texts.jsonl` 전체 6,849행 중 **`k`가 `\n`/`\r\n`으로 끝나는
행은 0개**다(전수 스캔, 위 스크립트를 `k_nl` 카운트로 바꿔 실행 — 출력 `k with trailing
nl count: 0`). 즉 이 파일의 `k` 필드는 원문에 개행이 있어도 전부 잘려 있다. 이건
「원문이 개행 없이 끝난다」는 뜻이 아니라 **추출 파이프라인이 `k`에서만 꼬리 공백류를
일관되게 지운다**는 뜻이다(아래 조사 2에서 그 이유가 나온다). 따라서 이 대칭성 검사
자체는 22행 판정에 쓸 수 없다 — k에 없다고 v도 없어야 한다는 근거가 안 된다.

## 조사 2 — 이 개행이 게임 키 정규화와 무슨 관계인가 (실측, 코드 근거)

`translate/build.py:61-73`의 `string_to_key()`는 게임의 `Messages.stringToKey`를
재현한 것이라고 주석에 적혀 있고, 꼬리 공백(개행 포함)을 지운다:
```python
def string_to_key(s):
    if re.search(r"[\r\n\t\x01]|(?m:^\s+|\s+$)|\s{2,}", s):
        s = re.sub(r"(?m)^\s+", "", s)
        s = re.sub(r"(?m)\s+$", "", s)
        s = re.sub(r"\s{2,}", " ", s)
    return s
```
이게 **키**에만 적용된다(`translate/build.py:131,153` — `*.add.jsonl`의 새 키를
등록할 때 호출). 기존 행(`translate/ko/*.jsonl` 본문)은 `row["k"] == keys[j]`로
**이미 정규화된 모양과 정확히 같은지**만 검사한다(`build.py:106,133` 부근) — 즉 절23의
`k`가 전부 개행 없이 끝나는 것은 **dat에 저장된 실제 키가 이미 그 모양이기 때문**이다.
게임이 `_INTL("...\n")`을 호출하면 조회 전에 인자를 같은 규칙으로 정규화해 키를 찾으므로,
dat의 키 자체는 개행이 빠진 채로 저장돼 있는 게 정상이다.

반면 **값(`v`)은 정규화되지 않는다** — `build.py:107`(`nv = row["v"].encode("utf-8")`)가
그대로 dat에 쓴다. 즉 `v`에 있는 꼬리 개행은 화면에 뜨는 텍스트 그대로 살아남는다.
**`k`에 개행이 없는 것과 `v`에 개행이 있어야 하는지는 서로 다른 질문이다** — 조사 1의
대칭성 검사가 무의미한 이유가 여기 있다. 답은 게임 소스가 그 `_INTL(...)` 호출을
어떻게 쓰는지에 달려 있다(조사 3).

## 조사 4 — 소비처: 통째 표시인가 연결 조합인가 (실측, 소스 발췌)

살아 있는 9행 전부 `+=` 연결로 여러 `_INTL(...)` 호출을 이어 붙여 한 화면 텍스트를
만드는 코드에 있고, **각 호출이 스스로 꼬리 개행을 달고 있다** — 이 개행이 줄 구분자
역할이라 빠지면 다음 조각과 한 줄로 붙어 버린다.

알 화면(3034·3036·5617, `<c3=...>` 색 태그가 붙은 요약 화면 텍스트):
```ruby
memo+=_INTL("<c3=404040,B0B0B0>{2} de {1} de {3}\n",month,date,year)   # → 3034
...
memo+=_INTL("<c3=404040,B0B0B0>Un extraño Huevo Pokémon hallado por <c3=F83820,E09890>{1}<c3=404040,B0B0B0>.\n",mapname)  # → 5617
...
memo+=_INTL("<c3=404040,B0B0B0>\"Estado del Huevo\"\n")   # → 3036
```
(`share/dist/…(BW)/Data/Scripts.rxdata` 디컴파일본, 오프셋 2893343 부근 — 재현은
위 조사 3 명령으로 같은 텍스트를 만들고 `full.find(...)`)

맵 편집기 도움말(3885·3886·3888·3889·3890·3891, RPG Maker 맵 편집 화면의 도움말
텍스트 — **플레이어가 아니라 맵을 손보는 개발자가 보는 화면**):
```ruby
helptext=_INTL("A: Agregar un mapa en el plano\r\n")
helptext+=_INTL("DEL: Borrar un mapa del plano\r\n")
helptext+=_INTL("S: Ir a otro mapa\r\n")
helptext+=_INTL("Clic para seleccionar un mapa\r\n")
helptext+=_INTL("Doble-clic: Editar metadatos del mapa\r\n")
helptext+=_INTL("E: Editar encuentros del mapa\r\n")
...
```
(같은 파일, `def helpWindow` 부근 — `S: Ir a otro mapa`는 우리 22행에 없다. `k`가
이미 `\r\n` 없이 저장돼 있고 `v`도 `\n` 없이 끝나 애초에 대상이 아니었다 — 즉 이
줄만 놓고 보면 형식이 이미 맞아 있었다는 뜻이고, 다른 여섯 줄과 나란히 있는데
**같은 화면의 형제 줄 하나만 다른 값**이라는 사실 자체가 다른 여섯 줄의 개행이
잡음이 아니라 정상 패턴이라는 방증이다.)

죽은 13행은 게임 소스 어디에도 문자열이 없으므로(조사 3의 4벌 전수 대조), 소비처
자체가 없다 — **연결 조합인지 통째 표시인지를 물을 자리가 없다.** 이건 "조회를 못
찾았다"가 아니라 "그 문자열이 소스에 없다"는 명시적 부재다(4벌 각각 독립적으로
`full.find()`가 -1을 반환 — 침묵이 아니라 없다는 관측 자체).

`"...\\\"Estado del Huevo\\\"\\n"` 같은 이중 이스케이프 오염분)이 정리된 흔적이다.
이 정리가 22행 판정에 영향을 주진 않는다.

## 한계

- 소스 대조는 `share/dist/`의 배포판 4벌(BW·DPPt·디버그 추가·갈무리)에 한정했다 —
  이 저장소가 직접 조립하는 완제품이라 범위 안이지만, **이 4벌 밖의(과거 릴리스,
  개발 중 미배포 브랜치) Scripts.rxdata는 보지 않았다.** "없음" 판정은 이 4벌
  전수에서의 명시적 부재이지(각각 `full.find()` == -1로 직접 확인), 침묵이 아니다.
- `\r\n`(맵 편집기)와 `\n`(알 화면)의 소스 리터럴이 **실행 시 정확히 그 바이트로
  치환된다**는 것은 확인했지만, RGSS(RPG Maker XP) 런타임이 그 문자열을 화면에
  그릴 때 `\r`을 어떻게 처리하는지(무시·줄바꿈 둘 다로 처리)까지는 확인하지 않았다
  — 맵 편집기는 플레이어 화면이 아니라 판정 무게가 낮아 더 파지 않았다.
- 22행이 「전부」인지는 처음 재현 명령의 정의(`v`가 `\r\n`/`\n`, `k`는 아님)에
  갇혀 있다 — 예를 들어 `k`도 `v`도 둘 다 개행으로 끝나는 행, 또는 `k`에만 있고
  `v`엔 없는 행은 이 조사 범위 밖이다(요청 정의를 그대로 따름).
