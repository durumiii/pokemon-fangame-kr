# 배포·릴리스

**범위** — 배포 zip을 릴리스에 올리고, 노트를 쓰고, 자산을 진열하는 규율.
**여는 때** — 새 판을 낼 때 · 릴리스 노트나 `읽어주세요.txt`를 쓸 때 · 릴리스 자산을
올리거나 라벨을 고칠 때.
**다루지 않는 것** — 배포물을 만드는 조립([packaging.md](packaging.md)).
**전제** — **릴리스는 유지자에게 물어보고 낸다.** 이 문서의 어떤 규칙도 그 앞에 서지 않는다.

## 릴리스 노트는 태그 diff에서 쓴다

기억으로 쓰면 그 앞 작업이 통째로 빠진다 — v5.2에서 커밋 86개·정본 1,384행이 노트에
한 줄도 안 실렸다.

1. `git log <직전태그>..HEAD --oneline | wc -l`로 규모부터 본다.
2. 사용자 체감 갈래(번역 품질 / 표기·용어 / 기능·결함 / 웹 / 배포)로 커밋을 훑고,
   `git diff <태그>..HEAD --numstat -- <경로>`로 규모를 센다. 행 수와 등장 횟수를
   섞지 않는다.
3. **배포물에 실제로 들어간 것만 적는다.** zip을 열어 확인한다 — 「쇠락」 아이콘은
   zip에 없었고(Z-GUI 모드 소유), 배포된 적 없는 모드를 적으면 거짓이 된다.
4. 노트와 zip 안 `읽어주세요.txt`를 **함께** 고친다 — 같은 재료로 쓰는 두 문서라
   한쪽만 고치면 누락이 그대로 남는다.

노트 본문(플레이어가 읽는 글)은 `docs/log/research/`에 판마다 두고, `docs/CHANGELOG.md`에는
유지자가 훑는 목록을 쌓는다.

## 자산 진열

GitHub는 자산을 **파일 이름순**으로 늘어놓는다 — 라벨 순서가 아니다.

- 차례는 파일 이름에 `01-`~`10-` 접두로 박는다(한 자리면 `10`이 `2`보다 앞선다).
  맨 끝에 둘 것은 `zz-`(지문 파일이 그 관례다).
- **라벨을 붙이면 화면에서 파일 이름이 가려진다.** 갈래가 여럿인 자산은 라벨에 갈래
  이름을 넣고(「한글패치 통합본 - 갈무리」), 파일 이름으로 충분한 것은 라벨을 안 붙인다.
- 라벨만 고칠 때 파일을 다시 올리지 마라 — API 한 줄이다:
  `gh api -X PATCH repos/<o>/<r>/releases/assets/<id> -f label="..."`.
  자산 id는 `gh api repos/<o>/<r>/releases/tags/<tag> --jq '.assets[] | "\(.id) \(.name)"'`.

## 판을 갈아 끼울 때

- 자산 교체는 받은 사람이 몇 안 될 때만 — 자산 URL이 새로 발급되므로 외부에 걸린
  직접 다운로드 링크는 깨진다(릴리스 페이지 주소는 그대로).
- 설치 안내는 **파일 단위 덮어쓰기**로 쓴다 — 「폴더를 통째로 덮어쓰라」는 모바일 파일
  관리자에서 폴더 교체로 읽혀 원판 `Data`가 통째로 사라진 제보가 있었다.
